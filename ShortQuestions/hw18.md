## Q0 - Explain following concepts, and how they coordinate with each other

### Topic
- A stream of data in Kafka, similar to a database table
- Producers write messages to a topic
- Consumers read messages from a topic
- A topic is split into partitions

### Partition
- A topic is divided into multiple partitions
- Each partition is ordered
- Order is guaranteed only within a partition
- Each message inside a partition has an incremental offset
- Partition improves scalability and parallelism

### Broker
- A Kafka server
- A Kafka cluster contains multiple brokers
- Each broker stores certain topic partitions
- For each partition, one broker is leader and others are replicas
- Only the leader handles read and write requests

### Consumer group
- A group of consumers sharing the same group id
- Consumers in the same group divide partitions among themselves
- Each partition is consumed by only one consumer in a group
- Enables parallel processing and load balancing

### Producer
- Writes data to topics
- Automatically decides which broker and partition to send data to
- If no key is provided, messages are distributed using round robin
- If key is provided, partition is determined by consistent hashing

### Offset
- Unique incremental id for each message in a partition
- Represents how far a consumer has processed
- Stored in internal topic `__consumer_offsets`
- Offset only has meaning within a specific partition

### Zookeeper
- Originally used for broker metadata management and cluster coordination
- Managed broker registration and leader election
- Being replaced by KRaft in newer Kafka versions

### How They Coordinate Together
- Producer sends messages to a Topic
- Topic is divided into Partitions
- Partitions are stored across Brokers
- One Broker acts as leader for each partition
- Consumers in a Consumer Group read from assigned partitions
- Each Consumer tracks its progress using Offset
- Zookeeper coordinates broker metadata and leader election

This coordination enables scalability, fault tolerance, parallel consumption, and data ordering within partitions

## Q1 - Given N (number of partitions) and M (number of consumers,) what will happen when N>=M and N<M respectively?

Where N is number of partitions, and M is number of consumers in the same consumer group:

### Case 1: N>=M
- Each partition can be assigned to only one consumer within a group
- Some consumers may consume multiple partitions
- All consumers can be active
- Maximum parallelism is limited by number of partitions
- Ideal scenario is N slightly greater than M

### Case 2: N<M
- Each partition can still be consumed by only one consumer
- Some consumers will remain idle
- Only N consumers can be active
- Extra consumers do not increase throughput
- Parallelism is limited by number of partitions

## Q2 - Explain how brokers work with topics?

### Topic Storage
- A topic is split into partitions
- Partitions are distributed across multiple brokers
- Each broker stores some partitions of a topic

### Leader and Replica
- For each partition, one broker is the leader
- Other brokers store replicas of that partition
- Leader handles all read and write requests
- Replicas synchronize data from the leader

### Fault Tolerance
- If a leader broker fails, a replica becomes the new leader
- This ensures high availability
- Replication factor determines how many copies exist

### Data Flow
- Producer connects to any broker called bootstrap broker
- Kafka returns metadata about which broker is leader for each partition
- Producer sends data directly to the leader broker
- Consumers also fetch data from the leader broker

## Q3 - Are messages pushed to consumers or consumers pull messages from topics?
Messages are pulled by consumers, not pushed by brokers

### Pull Model in Kafka
- Consumers actively request data from brokers
- Consumer sends fetch request to broker
- Broker returns available messages
- Consumer controls how fast it reads data

### Why Kafka Uses Pull
1. Better Scalability
    - Consumer decides its own consumption rate
    - Prevents overwhelming slow consumers
2. Backpressure Handling
    - Slow consumer simply polls less frequently
    - No need for broker to manage delivery speed
3. Batch Processing
    - Consumers can fetch messages in batches
    - Improves throughput and performance

## Q4 - How to avoid duplicate consumption of messages?
### 1. Commit Offset After Processing
- Disable auto commit
- Process the message first
- Commit offset only after successful processing
- Prevents losing messages
- May still cause duplicates if crash happens before commit

This is the correct baseline practice

### 2. Idempotent Consumer Logic
- Ensure processing the same message multiple times produces the same result
- Use unique business id or message key
- Store processed message ids in database
- Skip message if already processed

This is the most common real-world solution

### 3. Use Exactly-Once Semantics (EOS)
- Enable idempotent producer
- Enable Kafka transactions
- Use isolation.level = read_committed
- Consume and produce within a single transaction

Prevents duplicates in consume-process-produce pipelines

### 4. Use Unique Keys
- Same key always goes to same partition
- Helps maintain ordering
- Makes deduplication easier

## Q5 - What will happen if some consumers are down in a consumer group? Will data loss occur? Why?

### What will happen
1. Rebalance Happens
    - Kafka detects consumer failure through heartbeat timeout
    - Remaining consumers in the same group trigger a rebalance
    - Partitions from the failed consumer are reassigned
2. Partitions Are Reassigned
    - Each partition must still be consumed by one consumer in the group
    - Other active consumers take over those partitions
    - Consumption continues automatically

### Will Data Loss Occur?

Normally, no 

Reason:
- Messages are stored on brokers
- Data is retained for a configured retention period
- Messages are not deleted after being consumed
- Offset determines where consumer resumes

If the failed consumer had not committed its latest offset:
- New consumer will resume from last committed offset
- Some messages may be reprocessed
- This causes duplicate consumption, not data loss

Data loss can happen only if:
- Offsets were committed before processing
- Retention period expired before consumer resumed
- Replication factor is too low and broker fails without replica\

## Q6 - What will happen if an entire consumer group is down? Will data loss occur? Why?


### What will happen?
- No consumers are actively polling messages
- Messages continue to be written to the topic by producers
- Brokers store messages based on retention policy
- No rebalancing happens because the whole group is offline

### Will data loss occur?
Normally, no, because:
- Kafka stores messages independently of consumers
- Messages are retained for a configured time or size limit
- Offset is stored in `__consumer_offsets`
- When the group comes back, it resumes from last committed offset

When the group restarts, it may:
- Consumers rejoin the group
- Partitions are reassigned
- Consumption resumes from last committed offset
- Messages produced during downtime are still available

Data loss may occur if:
- Retention period expires before consumers restart
- Retention size limit is exceeded
- Replication factor is too low and brokers fail

## Q7 - Explain consumer lag and how to resolve it?

### What is Consumer Lag
Consumer lag is the difference between:
- Log End Offset
- Current Committed Offset

Lag = Log End Offset minus Consumer Offset

It represents how many messages the consumer has not yet processed.
Lag is calculated per partition and per consumer group.

### Why it Happens
1. Slow Consumer
    - Consumer processing time is too long
    - Heavy business logic or database calls
2. Too Few Consumers
    - Number of consumers is smaller than number of partitions
    - Not enough parallelism
3. Traffic Spike
    - Producer sends messages faster than consumers can process
4. Resource Bottleneck
    - CPU, memory, or network issues
5. Rebalance Delay
    - Frequent rebalances pause consumption temporarily

### How to Resolve
1. Increase Number of Consumers
    - Scale consumers horizontally
    - Must not exceed number of partitions
2. Increase Number of Partitions
    - Improves parallelism
    - Allows more consumers to work simultaneously
3. Optimize Consumer Logic
    - Reduce blocking operations
    - Use batch processing
    - Improve database performance
4. Tune Consumer Configurations
    - Increase fetch.min.bytes
    - Increase max.poll.records
    - Adjust session timeout and poll interval
5. Improve Infrastructure
    - Allocate more CPU or memory
    - Optimize network bandwidth

## Q8 - Explain how Kafka tracks message delivery?
Kafka tracks delivery using offsets per partition per consumer group

### 1. Offset Mechanism
- Each message in a partition has a unique incremental offset
- Offset represents the position of the message
- Consumers track how far they have processed
- Offset is stored per consumer group

Offset only has meaning within a specific partition

### 2. Consumer Offset Storage
- Kafka stores consumer offsets in an internal topic called __consumer_offsets
- When a consumer commits an offset, Kafka records it there
- On restart, consumer resumes from last committed offset

This allows fault tolerance and recovery

### 3. Commit Strategies
1. Auto Commit
    - Offsets are committed periodically
    - Simpler but may cause duplicates or data loss
2. Manual Commit
    - Application commits offset after successful processing
    - More reliable

### 4. Delivery Guarantees and Offset
At-most-once
- Commit before processing
- May lose messages

At-least-once
- Commit after processing
- May duplicate messages

Exactly-once
- Use transactions and idempotent producer
- Offset and output committed atomically

## Q9 - Compare Kafka vs RabbitMQ, compare messageing frameworks vs MySql (Why Kafka)?

### Kafka vs RabbitMQ

1. **Architecture**

Kafka
- Distributed log based system
- Data stored in partitions
- High throughput and horizontal scalability

RabbitMQ
- Traditional message queue
- Messages stored in queues
- Broker pushes messages to consumers

2. **Message Retention**

Kafka
- Messages retained for configurable time or size
- Messages are not deleted after consumption
- Consumers track offset

RabbitMQ
- Messages removed after being acknowledged
- Designed for short-term delivery

3. Delivery Model

Kafka

Pull model

Consumer controls consumption rate

Suitable for high throughput streaming

RabbitMQ

Push model

Broker pushes messages to consumers

Good for real-time task distribution

4. **Scalability**

Kafka
- Designed for big data and event streaming
- Handles millions of messages per second
- Partition-based scaling

RabbitMQ
- Good for moderate workloads
- Scaling is more complex

5. **Typical Use Cases**

Kafka
- Event streaming
- Log aggregation
- Real-time analytics
- Event-driven microservices

RabbitMQ
- Task queues
- Background job processing
- RPC style communication

### Messaging Frameworks vs MySQL (Why Kafka?)
1. **System Design Purpose**

MySQL
- Relational database
- Stores structured data
- Used for persistent business data

Kafka
- Distributed messaging system
- Used for event streaming
- Connects microservices

2. **Performance**

MySQL
- Optimized for transactions and queries
- Not designed for high throughput event streaming

Kafka
- Optimized for sequential disk writes
- High throughput and low latency

3. **Decoupling**

MySQL
- Services tightly coupled through shared database
- Harder to scale independently

Kafka
- Producer and consumer are decoupled
- Services communicate through events
- Supports asynchronous architecture

4. **Scalability**

MySQL
- Vertical scaling common
- Sharding adds complexity

Kafka
- Horizontal scaling via partitions
- Naturally distributed

5. **Reliability**

MySQL
- Single database may become bottleneck
- Strong ACID guarantees

Kafka
- Replication across brokers
- Fault tolerant
- Supports different delivery guarantees
