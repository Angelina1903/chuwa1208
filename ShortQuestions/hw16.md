## Q1 -  Three Pillars of Observability
**What are the three pillars of observability, and what is the primary purpose of each?**

The three pillars of observability are **Metrics**, **Logs**, and **Traces**

### Metrics
Numerical measurements collected over time

**Purpose**:
- Monitor system health
- Detect anomalies
- Trigger alerts
- Support autoscaling (e.g., HPA in Kubernetes)

**Key characteristic**:
- Aggregated and lightweight
- Best for trend analysis

Examples: CPU usage, Memory usage, Request rate, Error rate, Latency

### Logs
Time-stamped records of discrete events

**Purpose**:
- Provide detailed diagnostic information
- Help investigate specific failures
- Support root cause analysis

**Key characteristic**:
- High detail
- Unstructured or structured (JSON preferred in containers)

Examples: Application errors, Debug messages, User actions, System events

### Traces
Records of a request’s journey across multiple services

**Purpose**:
- Analyze distributed systems behavior
- Identify bottlenecks
- Debug latency issues in microservices

**Key characteristic**:
- End-to-end visibility of a single request

Tracks: Service-to-service calls, Latency at each step, Dependencies

## Q2 - Metrics Data Types 
**Explain the four common metric types and give an example use case for each.**
The four common metric types are **Counter**, **Gauge**, **Histogram**, and **Summary**

### Counter
- Definition: A metric that only increases over time (monotonically increasing)
- Can only reset when the application restarts
- Used to measure cumulative events
- Purpose: Track event rates (e.g., errors per second)

Sample Use Case:
- Total number of HTTP requests
- Total error count
- Number of processed messages

### Gauge
- Definition: A metric that can increase or decrease
- Represents the current state of a value
- Primary purpose: Monitor real-time resource usage or system state

Sample Use Case:
- Current memory usage
- Active thread count
- Number of open database connections

### Histogram
- Definition: Measures distribution of values and groups them into buckets
- Tracks count of observations in each range
- Primary purpose:
    - Analyze performance distribution
    - Calculate percentiles (e.g., P95 latency)

Sample Use Case:
- HTTP request latency (e.g., <100ms, 100–300ms, >300ms)
- Payload size distribution

### Summary
- Definition: Similar to histogram but calculates quantiles (percentiles) directly
- Provides aggregated statistical values
- Primary purpose: Direct percentile-based performance measurement

Example Use Case:
- 95th percentile request latency
- Median processing time

## Q3 - Structured Logging 
**What is structured logging, and why is it preferred over unstructured (plain text) logging in production systems?**

### What is Structured Logging
- Structured logging outputs logs in a machine-readable format
- Common format: JSON
- Logs contain clearly defined key–value pairs

### Why preferred over unstructured (plain text) logging in production systems?
1. Machine-Readable
    - Log aggregation systems can easily parse fields
    - No need for fragile regex extraction
2. Better Search & Filtering:
    - Query by specific fields
3. Improved Observability
    - Enables correlation between Logs, Metrics, and Traces
    - Supports distributed tracing via request IDs
4. Scalability
    - Modern systems generate large volumes of logs
    - Structured logs integrate cleanly with Centralized logging systems, Cloud monitoring platforms, and SIEM tools
5. Consistency Across Services
    - Standardized schema across microservices
    - Easier cross-service debugging


_Plus, Plain Text Logging Is Problematic Because it is_
- Hard to parse at scale
- Inconsistent formats
- Difficult to automate analysis
- Poor support for distributed systems

## Q4 - Distributed Tracing Concepts 
**Explain the relationship between Trace, Span, and Context Propagation in distributed tracing.**

### Trace
A trace represents the entire lifecycle of a single request. It covers all services involved in handling that request.

_A Trace is identified by a unique Trace ID_

### Span
A span represents a single unit of work within a trace. Each service call or internal operation creates a span. It cantains a Span ID, a Parent span ID, the Start and End time, and corresponding Metadata (tags, errors)

A trace is composed of multiple spans, which form a tree structure (parent-child relationships)

### Context Propagation
Context propagation passes tracing information between services. It ensures all spans belong to the same trace. This is usually done via HTTP headers (e.g., trace-id, span-id) or Messaging metadata

Without context propagation, each service would create a new trace, and the end-to-end visibility would be broken

## Q5 - Prometheus Pull Model 
**Prometheus uses a "pull" model for collecting metrics. Explain how this works and what are its advantages and disadvantages compared to a "push" model.**

### How the Prometheus Pull Model Works
- Applications expose metrics at an HTTP endpoint
- Prometheus periodically scrapes these endpoints
- Collected metrics are stored in a time-series database
- Targets are discovered via configuration or service discovery (e.g., Kubernetes)

### Advantages
1. Simpler Architecture
    - No need for applications to know where to send metrics
    - Centralized collection
2. Service Discovery Integration
    - Works well with Kubernetes service discovery
    - Automatically discovers new Pods
3. Health Visibility
    - If Prometheus cannot scrape a target, it immediately knows the target is unreachable
    - A missing scrape usually indicates that the service has crashed, is unhealthy, or there is a network issue

4. Better Security Control
    - Centralized access control
    - Fewer outbound connections from services

### Disadvantages
1. Not Ideal for Short-Lived Jobs
    - If a job finishes before next scrape, metrics may be lost
    - Requires Pushgateway for batch jobs
2. Network Accessibility Required
    - Prometheus must be able to reach targets
    - Harder in restricted or cross-network environments
3. Scrape Overhead
    - Large number of targets can increase load

## Q6 -  Control Plane Components 
**What are the four main components of the Kubernetes control plane, and what is the responsibility of each?**

### API Server (kube-apiserver)
- Central entry point for the cluster
- Exposes the Kubernetes REST API
- Validates and processes all requests (kubectl, controllers, etc.)
- Only component that directly communicates with etcd
- Responsibility: Acts as the front door and coordination hub of the cluster

### etcd
- Distributed key-value store
- Stores all cluster states: Pods, Deployments, Services, Configurations
- Responsibility: Maintains the single source of truth for the cluster

### Scheduler (kube-scheduler)
- Assigns newly created Pods to nodes
- Considers resource availability, node constraints, and affinity/anti-affinity rules
- Responsibility: Decides where Pods should run

### Controller Manager (kube-controller-manager)
- Runs control loops
- Ensures actual state matches desired state
- Includes controllers such as deployment controller, replicaSet controller, and node controller
- Responsibility: Continuously monitors and reconciles cluster state

## Q7 - kubelet 
**What is kubelet and what role does it play on a Kubernetes worker node?**

kubelet is the primary node agent in Kubernetes. It runs on every worker node and communicates with the Kubernetes control plane

### Role of kubelet on a Worker Node
1. Ensures Pods Are Running
    - Watches for Pod specifications assigned to the node
    - Ensures containers are started via the container runtime
    - Maintains the desired state of Pods
2. Interacts with the Container Runtime
    - Uses the Container Runtime Interface (CRI)
    - Starts, stops, and manages containers
    - Pulls container images
3. Reports Node and Pod Status
    - Sends pod status, node health, and resource usage
    - Allows the control plane to monitor cluster health
4. Handles Health Checks
    - Executes liveness, readiness, and startup probes
    - Restarts containers if needed

## Q8 - etcd 
**What is etcd in Kubernetes, and why is it critical to the cluster's operation?**

etcd is a distributed key-value store used by Kubernetes. It stores all cluster data and configuration. It acts as the persistent storage layer of the control plane

### Why Is etcd Critical?
1. Stores Desired and Current State
    - Controllers rely on etcd to reconcile state
    - All scheduling and orchestration decisions depend on it
2. Central Coordination Point
    - API Server reads from and writes to etcd
    - All cluster changes are persisted there
3. Cluster Recovery
    - Backups of etcd enable full cluster restoration
    - If etcd data is lost, cluster state is lost

## Q9 - kube-proxy 
**What is kube-proxy and how does it enable Service networking in Kubernetes?**

kube-proxy is a network component that runs on every node in Kubernetes. It manages networking rules for Kubernetes Services and enables communication between Services and Pods

### How kube-proxy Enables Service Networking
1. Implements Service Virtual IP (ClusterIP)
    - Each Service gets a virtual IP (ClusterIP)
    - kube-proxy configures network rules so traffic sent to the Service IP is forwarded to backend Pods
2. Load Balances Traffic
    - Distributes incoming requests across multiple Pod endpoints
    - Uses mechanisms like iptables and IPVS
    - This provides basic internal load balancing
3. Updates Rules Dynamically
    - Watches the API Server for New Services and Pod changes
    - Automatically updates networking rules when Pods are added or removed

## Q10 - Scheduler 
**How does the Kubernetes Scheduler decide which node to place a Pod on? What factors does it consider?**

### How the Scheduler Decides Node Placement
The scheduling process has two main phases:

1. Filtering (Feasibility Check)
    - Eliminate nodes that cannot run the Pod.
    - Factors considered:
        - CPU and memory availability (resource requests)
        - Node conditions (Ready, NotReady)
        - Taints and tolerations
        - Node selectors and node affinity
        - Volume constraints
    - _Only nodes that meet all requirements move to the next phase_

2. Scoring (Ranking)
    - Score remaining nodes to choose the best one
    - Factors considered:
        - Resource utilization balance
        - Affinity / anti-affinity rules
        - Topology spread constraints
        - Preferred scheduling rules
    - The node with the highest score is selected

### In summary, Key Factors Considered
Resource requests (CPU, memory)<br>
Node labels and selectors<br>
Taints and tolerations<br>
Affinity and anti-affinity rules<br>
Storage and volume requirements<br>
Topology constraints<br>
