### Q1 -  In the CAP theorem, why is Partition Tolerance (P) considered mandatory in a real distributed system? Given that P is mandatory, what is the actual trade-off a system designer must make?

#### Why Partition Tolerance (P) is mandatory
- Network partitions are unavoidable in real distributed systems (packet loss, network splits, node failures)
- A system cannot reliablt distinguish between a failed node and a slow or partitioned network
- Ignoring partitions would cause the system to fail entirely whenever communication breaks

#### Actual trade-off given P is mandatory
**CP (Consistency + Partition Tolerance)**
- May reject or block requests during a partition
- Guarantees strong consistency
- Examples: ZooKeeper, etcd, HBase

**AP (Availability + Partition Tolerance)**
- Always responds to requests, even during a partition
- May return stale or inconsistent data
- Examples: Cassandra, DynamoDB, DNS

### Q2 -  Explain the difference between linearizability and eventual consistency. Give one real-world system example for each.
#### Linearizability
- Guarantees that all operations appear to execute atomically in a single global order
- A read always returns the most recent completed write
- Behaves like a single machine from the client’s perspective
- Example: etcd

#### Eventual Consistency
- Guarantees that replicas will converge to the same value if no new updates occur
- Reads may return stale or different values during convergence
- Prioritizes availability and low latency
- Example: Amazon DynamoDB

### Q3 - What is a vector clock? How does it determine whether two events are causally related or concurrent? Why can't we simply use physical timestamps instead?

#### What is a vector clock?
- A logical clock that tracks causality in a distributed system
- Represented as a vector of counters, one per node
- Each node increments its own counter on local events and merges vectors on message receipt

#### How it determines causality vs concurrency?
Event A **happened-before** event B if:
- All components of A’s vector clock ≤ B’s vector clock, **and**
- At least one component is strictly smaller

Two events are **concurrent** if:
- Neither vector clock is ≤ the other (the vector clocks are incomparable)

#### Why not use physical timestamps?
- Physical clocks are not perfectly synchronized 
- A later timestamp does not guarantee a causally later event
- Can lead to causality violations

### Q4 -  In single-leader replication, what is the split-brain problem during failover, and why is it dangerous?
#### What is the Split-brain problem
- Occurs when multiple nodes believe they are the leader at the same time
- Typically happens during network partitions or incorrect failure detection in failover

#### Why is it dangerous?
- Multiple leaders accept writes concurrently
- Causes conflicting writes and data divergence between replicas
- Merging divergent states is difficult or impossible without data loss
- Violates consistency guarantees of the system

### Q5 - Describe the quorum condition (W + R > N) in leaderless (Dynamo-style) replication. What happens if this condition is not satisfied?
#### **Quorum condition (W + R > N)**
**N**: total number of replicas for a data item

**W**: minimum number of replicas that must acknowledge a write

**R**: minimum number of replicas queried for a read

**W + R > N** guarantees that the read set overlaps with the latest successful write set, enabling the client to return the newest version by selecting the highest-versioned value from the read quorum

#### If the condition is not satisfied
- Read and write quorums may not overlap
- Reads can return stale data even after a successful write
- Consistency is no longer guaranteed (system behaves as “best-effort” eventual consistency)
- Conflicts and anomalies become more frequent and harder to resolve

### Q6 - Compare Two-Phase Commit (2PC) and the Saga pattern for distributed transactions. What is the main weakness of 2PC that Saga avoids, and what guarantee does Saga sacrifice in return?

#### Two-Phase Commit (2PC)
- Provides strong atomicity across multiple nodes
- All participants either commit or abort together
- Uses distributed locking during the transaction
- Weakness: a blocking protocol -- participants can be stuck waiting if the coordinator fails

#### Saga Pattern
- Breaks a transaction into a sequence of local transactions
- Uses compensating actions to undo completed steps on failure
- Avoids global locks and blocking
- Trade-off: does not provide atomicity or isolation; only eventual consistency


**Weakness avoided by Saga**: blocking and resource lock-up caused by coordinator failure in 2PC <br>
**Guarantee sacrificed by Saga**: strong ACID guarantees (especially atomicity and isolation)

### Q7 -  In the Raft consensus algorithm, why does a candidate need its log to be at least as up-to-date as the majority of the cluster in order to win an election? What safety property does this guarantee?

#### Why must have an up-to-date log?
- Prevents a node with missing committed entries from becoming leader
- A candidate’s log is considered at least as up-to-date if:
    - Its last log term is higher than others’, or
    - The last log term is equal and its log is longer
- Followers only vote for candidates whose logs are at least as up-to-date as their own
- This ensures the elected leader has all entries that were committed by a majority

#### Safety property guaranteed
- Leader Completeness (Log Safety): Once a log entry is committed, it will never be lost, and all future leaders will contain that committed entry

### Q8 -  What is a CRDT (Conflict-free Replicated Data Type)? Explain how a G-Counter works and why it always converges without coordination.

#### What is a CRDT
- A data type designed for distributed systems
- Allows multiple replicas to be updated independently without coordination
- Guarantees eventual convergence through mathematically defined merge rules
- Resolves conflicts automatically without locks or consensus

#### How a G-Counter works
- A grow-only counter where each replica maintains its own local counter
- Increment operations only affect the local replica’s counter
- The total value is the sum of all replica counters
- Merge operation takes the element-wise maximum of counters from each replica

#### Why it always converges
- Operations are monotonic (counters only increase)
- Merge is: Commutative (order doesn’t matter), Associative, and Idempotent
- Repeated merges eventually produce the same state on all replicas, regardless of message order or duplication

### Q9 - Explain the Circuit Breaker pattern. What are its three states, and how does it prevent cascading failures in a microservices architecture?

The Circuit Breaker patter is a resilience pattern that prevents repeated calls to a failing service. It stops failures from propagating and overwhelming dependent services, and also protects system availability and latency under partial failures

#### The Three states
- **Closed**
    - Normal operation
    - Requests flow through
    - Failures are counted

- **Open**
    - Triggered when failure threshold is exceeded
    - All requests are rejected immediately (fast fail)

- **Half-Open**
    - After a cooldown period
    - Allows a limited number of test requests
    - If successful: transition to Closed
    - If failed: transition back to Open

#### How it prevents cascading failures
- Fails fast instead of waiting on slow or failing downstream services
- Reduces resource exhaustion (threads, connections, CPU)
- Gives failing services time to recover
- Enables graceful degradation and fallback behavior

### Q10 -  What is the difference between range-based partitioning and hash-based partitioning? What problem does consistent hashing solve compared to simple hash-mod-N partitioning?

#### Range-based partitioning
- Partitions data by key ranges
- Keys in the same range are stored on the same shard
- Efficient for range queries
- Prone to hot spots and uneven load distribution

#### Hash-based partitioning
- Partitions data using a hash function on the key
- Provides uniform data distribution across shards
- Avoids hot spots for random keys
- Range queries require querying all shards

#### Problem solved by consistent hashing
- Simple hash-mod-N requires rehashing almost all keys when the number of nodes changes
- Consistent hashing minimizes data movement when nodes are added or removed
- Only a small fraction of keys are remapped
- Improves scalability and operational stability
