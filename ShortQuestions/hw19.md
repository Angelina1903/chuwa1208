## Q1 - Thread vs Async
**When should you use multi-threading versus async/non-blocking I/O? Give specific examples of scenarios for each approach.**

### When to use multi-threading
- CPU-bound tasks
- High CPU utilization, low I/O wait
- Need parallel computation across cores
- Blocking code is acceptable

Examples:
- Image/video processing
- Encryption / hashing
- Large data sorting
- Heavy JSON parsing
- Batch data transformation

**Why**:
- Utilizes multiple CPU cores
- Async provides no benefit for pure computation

### When to use Async / Non-blocking I/O
- I/O-bound tasks
- High I/O wait (DB, HTTP, file, MQ)
- Very high concurrency (10K+ requests)
- Want to avoid thread-per-request model

Examples:
- REST API calling multiple downstream services
- API Gateway aggregation
- Chat server with many connections
- High-concurrency DB query service

**Why**:
- Threads blocked on I/O waste memory (~1MB each)
- Event loop model scales better under heavy I/O
- Prevents thread exhaustion

## Q2 - Virtual Threads (Java 21) 
**What are Virtual Threads in Java 21? Explain how they differ from platform threads and when you should (or should not) use them.**

### What are Virtual Threads?
- Lightweight threads managed by the JVM (not 1:1 mapped to OS threads)
- Goal: make blocking I/O scale like async, but keep simple synchronous code

### Virtual Threads vs Platform Threads

Platform thread
- 1 request ≈ 1 OS thread
- Large stack (~MB level) → limited concurrency

Virtual thread
- 1 request ≈ 1 JVM virtual thread
- Much smaller stack (KB level) → can handle massive concurrency 


Key difference
- Platform threads block an OS thread on I/O
- Virtual threads can park/unpark cheaply so blocking doesn’t “waste” an OS thread (JVM schedules them)

### When to use
- High I/O wait workloads: DB queries, HTTP calls, file/network I/O
- Many concurrent connections
- Want blocking style code (easy to write/debug) but need async-like scalability

Examples:
- Typical Spring Boot service with lots of DB/remote calls
- High-concurrency API service where most time is waiting on I/O

### When to NOT use
- CPU-intensive computation (no benefit, CPU is the bottleneck)
- Heavy use of synchronized blocks (can reduce scalability)
- Long-lived reliance on ThreadLocal (can be problematic at scale) 

Examples:
- Image processing / crypto / ML inference
- Highly synchronized shared-state logic

## Q3 - Lock vs CAS 
**Compare Lock-based synchronization and CAS (Compare-And-Swap). When would you choose one over the other?**

### Lock-based Synchronization
How it works:
- Uses mutex / synchronized / ReentrantLock
- Only one thread enters critical section
- Other threads are blocked (sleeping) 

Characteristics:
- Threads may incur context switching overhead
- Protect multiple variables / complex operations
- Support fairness policies

**When to use**:
- Critical section involves multiple shared variables
- Logic is multi-step and must be atomic
- Contention is high and CPU spinning is undesirable

Example:
- Money transfer between accounts
- Updating several related fields together

### CAS (Compare-And-Swap)
How it works:
- Lock-free, uses CPU atomic instruction
- Thread reads value → attempts CAS update
- If conflict → retry (spin) 

Characteristics:
- No blocking
- No context switch
- May waste CPU under high contention (spinning)
- Works best for single-variable updates

**When to use**:
- Simple counters / flags
- Low contention scenarios
- Need high performance for atomic updates

Example:
- Incrementing request counter
- Updating status flag

## Q4 - Deadlock Conditions (Difficult) 
**What are the four necessary conditions for a deadlock to occur? Explain how "lock ordering" prevents deadlock.**

### Four Necessary Conditions for Deadlock

Deadlock occurs only if all four conditions are present:
1. Mutual Exclusion
    - A resource can be held by only one thread at a time

2. Hold and Wait
    - A thread holds at least one resource while waiting for another

3. No Preemption
    - A resource cannot be forcibly taken away; it must be released voluntarily

4. Circular Wait
    - A cycle exists where:
        - Thread A waits for a resource held by Thread B,
        - Thread B waits for a resource held by Thread A (or longer cycle)

If any one of these conditions is broken, deadlock cannot occur

### How Lock Ordering Prevents Deadlock

Lock ordering prevents the Circular Wait condition

Idea:
All threads must acquire locks in a consistent global order

Example problem:
- Thread 1 locks A then tries to lock B
- Thread 2 locks B then tries to lock A

This creates circular wait

Solution:<br>
Define a fixed rule, such as:<br>
Always lock the object with smaller ID first

So both threads will:
- Lock the smaller ID resource
- Then lock the larger ID resource

Because every thread follows the same order, a cycle cannot form.
Without circular wait, deadlock is impossible.

## Q5 - Thread Pool Sizing 
**What is the formula for calculating optimal thread pool size? How would you size a thread pool for**: 
- **A CPU-bound task on an 8-core machine?**
- **An I/O-bound task where wait time is 100ms and compute time is 5ms?**

### Thread Pool Sizing Formula
Optimal threads = `N_cpu × (1 + W/C)`
- `N_cpu` = number of CPU cores
- `W` = wait time (I/O wait)
- `C` = compute time (CPU work)

### Case 1: CPU-bound task on an 8-core machine
CPU-bound implies `W/C ≈ 0`<br>
Threads = `8 × (1 + 0) = 8`<br>

Recommended size: Around 8 threads (roughly equal to core count)

### Case 2: I/O-bound task (W = 100ms, C = 5ms)
`W/C = 100/5 = 20`<br>
Threads = `N_cpu × (1 + 20)` = `N_cpu × 21`<br>
If using the same 8-core machine: Threads = `8 × 21` = `168`

## Q6 - Exponential Backoff with Jitter 
**What is exponential backoff with jitter? Why is jitter important when implementing retry logic?**

### What is Exponential Backoff?
- Retry delay increases exponentially after each failure
- Typical pattern:
    - Attempt 1 → wait 100ms
    - Attempt 2 → wait 200ms
    - Attempt 3 → wait 400ms
    - Attempt 4 → wait 800ms
- Usually capped at a maximum delay
- Purpose:
    - Give failing service time to recover
    - Reduce immediate retry pressure

### Why Jitter Is Important
Without jitter:
- All clients retry at the same time
- Creates synchronized retry spikes
- Causes thundering herd problem
- Can overwhelm already struggling service 

With jitter:
- Retries are spread out
- Load is distributed over time
- Reduces retry storm risk
- Improves system stability

**What is Jitter?**
- Add randomness to the backoff delay
- Instead of fixed delay: delay = base × 2^attempt
- Use: delay = base × 2^attempt + random(0, delay)
- Each client waits a slightly different time

## Q7 - Circuit Breaker Pattern (Difficult) 
**Explain the three states of a Circuit Breaker (CLOSED, OPEN, HALF-OPEN) and how transitions between them work.**

### Circuit Breaker Pattern
A circuit breaker protects the system from repeatedly calling an unhealthy downstream service

### CLOSED State
- Default state
- All requests are allowed to call downstream service
- System monitors:
    - Failure rate
    - Slow call rate

Transition condition:
- If failure rate exceeds configured threshold, the state changes to OPEN

### OPEN State
- All requests fail immediately
- No downstream call is attempted
- Purpose:
    - Prevent resource waste
    - Allow downstream service time to recover 

Transition condition:
- After a configured wait duration, the state changes to HALF-OPEN

### HALF-OPEN State
- Allows a limited number of test requests
- Used to check if downstream service has recovered

Transition conditions:
- If test requests succeed, state changes to CLOSED
- If test requests fail, state changes back to OPEN

## Q8 - Exactly-Once Semantics (Difficult) 
**Why is "exactly-once delivery" considered impossible in distributed systems? How can you achieve "exactlyonce processing" instead?**

### Why "Exactly-Once Delivery" Is Impossible
In distributed systems, message delivery cannot be guaranteed to happen exactly once due to network uncertainty

Reasons:
- Network can drop responses after the server has processed the request
- Client may timeout and retry
- Server may process the same request again
- There is no way to distinguish:
    - “Request not processed”
    - “Request processed but response lost”

Because of retries + unreliable networks, delivery is realistically:
- At-least-once
- Or at-most-once

But not truly exactly-once

### How to Achieve “Exactly-Once Processing”
Instead of guaranteeing delivery, guarantee idempotent processing

Core idea:
- Make operations idempotent
- Same request repeated multiple times produces the same result

**Idempotency Implementation Pattern**<br>
Use an idempotency key:
- Client generates unique request ID
- Server checks if this key was already processed
- If yes:
    - Return stored result
    - Do not execute business logic again
- If no:
    - Execute operation
    - Store result with idempotency key

## Q9 - Caching Patterns 
**Compare the three caching patterns: Cache-Aside, Write-Through, and Write-Behind. What are the trade-offs of each?**

### Cache-Aside (Lazy Loading)
**How it works**:
- On read:
    - Check cache
    - If miss → load from DB
    - Store in cache
- On write:
    - Update DB
    - Invalidate or update cache

**Pros**:
- Simple and most common
- Good read performance
- No write latency overhead from cache

**Cons**:
- Eventual consistency (stale data until TTL or invalidation)
- Risk of cache stampede
- Application must manage invalidation

**Best for**:
- General-purpose systems
- Read-heavy workloads

### Write-Through
**How it works**:
- On write:
    - Write to cache
    - Write to DB synchronously
- Read served from cache

**Pros**:
- Strong consistency between cache and DB
- Simple mental model
- Always up-to-date cache

**Cons**:
- Higher write latency
- Write amplification
- Cache may store rarely used data

**Best for**:
- Read-heavy systems requiring stronger consistency

### Write-Behind (Write-Back)
**How it works**:
- On write:
    - Write to cache
    - Return immediately
    - Async process flushes to DB later

**Pros**:
- Very fast write performance
- Good for high write throughput
- Can batch writes to DB

**Cons**:
- Eventual consistency
- Risk of data loss if cache crashes before flush
- More complex implementation

**Best for**:
- Write-heavy workloads
- Systems that tolerate eventual consistency

## Q10 - Cache Stampede 
**What is cache stampede (also known as cache breakdown)? Describe two solutions to prevent it.**

### What is Cache Stampede?
- Happens when a hot cache key expires
- Many concurrent requests see cache miss at the same time
- All requests hit the database simultaneously
- Database becomes overloaded or crashes

Typical scenario:
- Key expires
- 1000 concurrent requests
- 1000 DB queries triggered
- DB overwhelmed

### Solution 1: Locking (Single Recompute)
Idea:
- Only one thread rebuilds the cache
- Other threads wait or return stale data

How it works:
- On cache miss:
    - Acquire lock for that key
    - Double-check cache after acquiring lock
    - If still missing, load from DB and update cache
- Other threads:
    - Wait for lock
    - Or retry later

Benefit:
- Prevents multiple simultaneous DB queries
- Ensures only one recomputation

### Solution 2: Early Refresh / Probabilistic Expiration
Idea:
- Refresh cache before it actually expires
- Avoid sudden simultaneous expiration

How it works:
- As TTL approaches expiration: Randomly trigger background refresh
- Cache never fully expires for all requests at once

Benefit:
- Smooth refresh over time
- Prevents sudden spike to DB
